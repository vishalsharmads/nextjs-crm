# Compliance readiness

This CRM ships the technical controls that privacy and health-data laws expect. It does not make a workspace compliant by itself: the operator still needs the agreements (DPA, BAA), policies, hosting safeguards and staff training the law requires. This document describes what the software does. The operator decides how to use it.

## Profiles

An admin picks a profile under **Settings → Compliance**. Only admins can change the Security and Compliance settings, because they weaken or strengthen every account's protection. A profile sets minimum settings (floors). While it is active:

- the server applies the floors on every read, even if a stored value is lower;
- saving a setting below a floor is rejected with a validation error that names the field;
- switching to a stricter profile raises the stored values right away (and records it in the audit log).

| Profile     | For                                                                         | Floors                                                                                                                                                                                                                                                                                                                                                    |
| ----------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Standard    | Workspaces with no special obligations                                      | None                                                                                                                                                                                                                                                                                                                                                      |
| Privacy     | Personal data under GDPR, UK GDPR, DPDP (India), CCPA/CPRA, PIPEDA and LGPD | Audit and access logs kept for at least 365 days (or forever); privacy requests answered within 30 days                                                                                                                                                                                                                                                   |
| Health data | Protected health information under HIPAA                                    | Everything in Privacy, plus: 2FA for every user, password of at least 12 characters with mixed case and a digit, lockout after at most 5 failures, sign-out after at most 15 minutes of inactivity, sessions of at most 12 hours, API keys that expire within 365 days, access logging on, audit and access logs kept for at least six years (or forever) |

## Controls

### Access and authentication

| Control                      | Where                                      | Notes                                                                                                                                                                 |
| ---------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unique user accounts         | Settings → Users                           | No shared logins; API keys are separate, hashed, and scoped by permission.                                                                                            |
| Password policy and lockout  | Settings → Security                        | argon2id hashes; minimum length, character mix, lockout threshold and duration.                                                                                       |
| Two-factor authentication    | Profile; Settings → Security / Compliance  | TOTP. Can be required for admins, for chosen roles, or for everyone. Users who must enrol are held on their profile page until they do.                               |
| Recovery codes               | Profile                                    | Ten single-use codes issued when 2FA is turned on, shown once and stored hashed. Using one is audited; users can replace them with their password.                    |
| Automatic logoff             | Settings → Compliance                      | Warning one minute before the limit, then sign-out. The server enforces the same limit, judged by the user's last keyboard or pointer input, not background requests. |
| Maximum session length       | Settings → Compliance                      | Forces a new sign-in after a fixed number of hours, active or not.                                                                                                    |
| API key lifetime             | Settings → Compliance, Settings → API keys | Optional maximum age. New keys must expire within it, and older keys stop working once they pass it. Keys are not subject to idle or session limits.                  |
| Sign-in notice               | Settings → Compliance                      | Free text under the sign-in form, for example an authorized-use warning.                                                                                              |
| Role-based access and scopes | Settings → Roles                           | Permissions per action; record scope own / team / all; per-role field visibility for custom fields.                                                                   |
| Audit log                    | Settings → Audit log                       | Every change, sign-in, failed sign-in, 2FA event, session expiry and export. Append-only (database triggers).                                                         |

### Accountability and audit

| Control             | Where                                                                  | Notes                                                                                                                                                                                                                                                                                                                        |
| ------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Audit log           | Settings → Audit log, Changes                                          | Every create, update, delete, sign-in, 2FA event, setting change and export, with actor, IP address, request id and a field-level diff. Custom fields hidden from the viewer are removed from diffs when they read the log.                                                                                                  |
| Access log          | Settings → Audit log, Access                                           | When access logging is on: who opened a record, downloaded a file, exported a list, or read the audit log. Required by the Health data profile. Modules (bookings, tickets, documents) do not log reads yet.                                                                                                                 |
| Export              | Audit log → Export CSV                                                 | Needs the `core.audit.export` permission. Exports are themselves audited. Use them for access reviews and incident investigations.                                                                                                                                                                                           |
| Append-only storage | Database triggers                                                      | Updates are refused except during privacy erasure (which redacts personal data and is audited); deletes are refused except by the retention job.                                                                                                                                                                             |
| Tamper evidence     | Audit log → Check integrity, `npm run cli -w @app/api -- audit:verify` | Each finished UTC day is sealed with a SHA-256 digest of its rows, chained to the previous day. Verification recomputes them: a changed, inserted or deleted row, or an edited digest, is reported. Digests are also written to the application log; ship that log off the server so a copy survives a compromised database. |
| Log retention       | Settings → Compliance                                                  | Entries older than the retention period are deleted hourly, only on days already sealed, and the deletion is audited. Digests of deleted days are kept.                                                                                                                                                                      |

### Data subject rights and consent

| Right or control            | Where                                   | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request tracker             | Settings → Privacy                      | Log every request (access, portability, correction, erasure, restriction, objection, do not sell or share) when it arrives. The due date comes from **Days to answer a privacy request** (Privacy and Health data profiles: at most 30). Overdue requests are flagged and the assignee is reminded three days before the due date.                                                                                                                              |
| Access and portability      | Privacy → request → Download their data | One ZIP: `personal-data.json` (the record with every field, activities, email copies, deals, consents, privacy requests, change history and every module's data) plus their files. The download is audited and access-logged.                                                                                                                                                                                                                                   |
| Correction                  | The record page                         | Edit the record; the change is audited.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Erasure                     | Privacy → Erase personal data           | Keeps the record for reports but clears personal details everywhere: the record and its custom fields, notes, email copies, files, webhook payloads, background jobs, automation logs, notifications, audit diffs and module data (portal accounts, ticket text, booking notes, visitor details). Consent proof stays without the IP address. Data the law requires you to keep (issued quotes, invoices, contracts, signed documents) is listed in the report. |
| Permanent deletion          | Privacy → Delete permanently            | Removes the record and the same copies. Needs a typed confirmation code. Refused while signed documents exist. The privacy request stays as proof, unlinked.                                                                                                                                                                                                                                                                                                    |
| Restriction (GDPR Art. 18)  | Privacy → Restrict processing           | The record stays stored but automations, webhooks and CRM email skip it. Shown on the record's Privacy tab.                                                                                                                                                                                                                                                                                                                                                     |
| Consent                     | Settings → Compliance; record → Privacy | Purposes have a key, wording and lawful basis. Every decision is stored append-only with the exact wording, its SHA-256 hash, the time, the source and the IP address. Staff can record consent given on the phone or on paper.                                                                                                                                                                                                                                 |
| Consent on web forms        | Settings → Web forms                    | Pick purposes per form; each shows an unticked checkbox, and required ones must be ticked. Only ticked boxes are recorded.                                                                                                                                                                                                                                                                                                                                      |
| Unsubscribe and do not sell | Link in automated email                 | Automated email to a contact or lead carries an unsubscribe link and a one-click `List-Unsubscribe` header. Unsubscribing withdraws every marketing purpose; the page also offers "Do not sell or share my personal information", logged as a completed request. People who opted out get no automated email.                                                                                                                                                   |
| Former staff                | Users → Erase, or `user:anonymize`      | Erases a disabled user's name, email, sign-in data, mailboxes and notifications. Their audit entries remain under an anonymous name.                                                                                                                                                                                                                                                                                                                            |

Later Phase 5 milestones add data retention and encryption of sensitive fields. This document grows with them.
